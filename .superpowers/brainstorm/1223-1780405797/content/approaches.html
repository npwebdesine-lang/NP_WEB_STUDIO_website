Architecture — 3 Approaches

All three use Next.js App Router + Tailwind + GSAP. The difference is how the complex vanilla modules (Three.js scene, custom cursor, animations) are structured in React.

A

Hook-per-module (Recommended)

Each vanilla JS singleton becomes a custom React hook: useThreeScene(), useCursor(), useGSAP() from @gsap/react. Hooks are mounted in the component that owns the DOM ref. Clean, testable, follows the @gsap/react docs exactly. Three.js stays imperative inside the hook — no extra library.

Pros

  • 1:1 mapping to existing modules
  • Easiest to migrate incrementally
  • @gsap/react useGSAP is the exact pattern requested

Cons

  • Three.js still imperative (not "React-native")
B

React Three Fiber (R3F) for the 3D scene

Replace raw Three.js with @react-three/fiber — JSX-based 3D rendering. Cursor and GSAP stay as hooks. The blob becomes a declarative <mesh> inside a <Canvas> component.

Pros

  • More idiomatic React 3D
  • Easier to animate mesh properties with @react-spring or GSAP

Cons

  • Full rewrite of scene.js shaders in R3F
  • Heavier bundle (+R3F ~250KB)
  • Existing shader code doesn't port cleanly
C

Vanilla singletons mounted via useEffect

Keep scene.js, cursor.js, animations.js as-is. Mount them inside useEffect with a canvas ref — minimal React wrapping. Fastest to ship but fights React's rendering model.

Pros

  • Zero rewrite of working code
  • Fastest initial delivery

Cons

  • Memory leaks if cleanup is wrong
  • Doesn't use @gsap/react useGSAP (user's requirement)
  • Hard to extend
